# 测试用例设计说明

本文说明「为什么这么设计用例」，而不只是「有哪些用例」。用例明细见
[`testcases/自动化测试用例.csv`](../testcases/自动化测试用例.csv)。

---

## 1. 被测对象与范围

| 项目 | 内容 |
|---|---|
| 系统 | 洞见微信（wechat.doonsec.com）—— 安全圈微信公众号文章全文检索平台 |
| 被测模块 | 首页与导航、全文搜索、内容分类展示、公众号与文章入口 |
| 覆盖方式 | Web UI 自动化（Python + Selenium + pytest） |
| 用例规模 | 30 条手工设计用例 + 5 条数据驱动用例 |
| 不在范围 | 登录/扫码鉴权、文章详情页正文渲染、后端接口、性能与兼容性 |

**为什么先选这四个模块**：它们构成「进入站点 → 找到内容 → 定位分类 → 抵达文章」
的完整主链路。主链路一旦断裂，后续所有业务都无法验证，属于测试优先级最高的部分。

---

## 2. 测试分层

用例不是平铺的 30 条，而是按目的分层，便于不同场景下选择执行子集：

| 层次 | 目的 | 典型用例 |
|---|---|---|
| L1 可达性 | 站点能否打开、页面骨架是否渲染 | `test_01`、`test_09` |
| L2 界面渲染 | 关键元素是否可见、属性是否正确 | `test_03`、`test_10`、`test_11` |
| L3 功能正确性 | 输入、点击、提交是否产生预期结果 | `test_12`、`test_16`、`test_21` |
| L4 结构与回归 | 操作后页面结构是否被破坏、历史缺陷是否复发 | `test_23`、`test_24` |
| L5 数据驱动 | 同一逻辑换多组数据批量验证 | `test_31~035` |

L1/L2 失败通常代表环境或站点不可用，应先修环境再看 L3 结果；否则会得到一堆
"假失败"，浪费排查时间。

---

## 3. 用例设计方法

### 3.1 等价类划分 —— 用最少用例覆盖输入域

搜索引擎的关键词输入可以划分为：

| 类 | 示例 | 是否有效 | 对应用例 |
|---|---|---|---|
| 英文缩写 | `CVE`、`POC` | 有效 | `test_12`、`test_18` |
| 中文短语 | `漏洞复现`、`弱口令` | 有效 | `test_13`、`test_33` |
| 中英混合 | `SQL注入` | 有效 | `test_34` |
| 空输入 | 不填直接提交 | 无效 | 本轮未纳入自动化，列入待补充项 |

### 3.2 边界值分析 —— 关注"刚好"的那一侧

- 页面链接数量断言使用 `> 5` 而不是 `== N`：**精确数量会随内容更新而失效**，
  是典型的脆弱断言。这里断言的是"结构未塌陷"这个业务不变量，而非具体数字。
- `test_23` 的 `> 5` 下限，对应历史缺陷中"点击分类后链接数掉到 0~2"的异常态。

### 3.3 场景法 —— 按用户真实路径串起来

```
场景：安全研究员想查某个漏洞的分析文章
  打开首页 → 点击「高级搜索」→ 进入 /es → 输入 CVE → 提交 → 结果页可达
对应：test_01 → test_08 → test_09 → test_16
```

单条用例各自通过，不代表场景通过。因此 `test_08` 特意写成"点击后校验 URL 已切换"，
而不是只校验"按钮点得动"。

### 3.4 错误推测法 —— 从"这里最容易坏"出发

| 推测的风险 | 设计的用例 |
|---|---|
| 导航是 JS 绑定，点击不一定跳转 | `test_08` 断言最终 URL，而非只断言点击动作 |
| 分类点击后内容区被清空（**历史真实缺陷**） | `test_23` 断言操作后链接数量 |
| 输入框二次输入时未清空旧值 | `test_18` 先输 `CVE` 再输 `POC`，断言最终值为 `POC` |
| 中文字符输入乱码/被截断 | `test_13` 断言回填值严格等于 `漏洞复现` |

### 3.5 参数化 —— 把复制粘贴变成数据

`test_05_keyword_data_driven.py` 把「输入→提交→结果页可达」抽成参数化用例，
5 个关键词 = 5 条用例，但只有 1 份逻辑。新增关键词只需在 `SEARCH_KEYWORDS`
里加一行 `pytest.param(...)`，不必新增函数。

## 4. 元素定位策略

本框架**有意使用了 5 种不同的定位方式**，不是为了炫技，而是每种都有适用场景：

| 定位方式 | 使用位置 | 选择理由 |
|---|---|---|
| `CSS_SELECTOR` | `.logo img`、`.search_form button` | 层级关系清晰、执行速度快，优先选择 |
| `CLASS_NAME` | `search_pic` | 单一 class 唯一标识，最短写法 |
| `NAME` | `keyword` | 表单字段的语义属性，比样式 class 稳定 |
| `LINK_TEXT` | `公众号` | 文本即业务含义，改版风险最低 |
| `PARTIAL_LINK_TEXT` | `高级搜索` | 链接文本可能带图标或后缀，用部分匹配更稳 |
| `XPATH` | `//li[@id='new']` | 需要按 `id` + 标签类型双重限定时使用 |
| `TAG_NAME` | `a`、`li` | 需要批量取同类元素做统计（如链接数量）时使用 |

**优先级原则**：`id` > `name` > `css` > `xpath` > 文本定位。
文本定位虽稳但受多语言影响；`xpath` 绝对路径（`/html/body/div[3]/...`）一律不用，
因为它对任何布局调整都 100% 敏感。

## 5. 稳定性设计（把 flaky 挡在框架层）

UI 自动化最常见的失败不是"功能坏了"，而是"时机不对"。本框架的处理：

| 问题 | 处理方式 |
|---|---|
| 元素还没渲染完就操作 | 全部走 `WebDriverWait` 显式等待，禁止 `time.sleep` 等固定时长 |
| 元素被固定导航栏遮挡点不到 | `scroll_to_element()` 先滚到视口中间再点 |
| 每条用例重复打开浏览器，慢且易触发反爬 | `driver` fixture 设为 `scope="session"`，全流程复用同一窗口 |
| 点击不跳转导致偶发失败 | 在 Page 层做 href 兜底跳转，把不稳定因素锁在页面对象内部 |
| 失败后无法复现 | 失败自动截图 + 记录当前 URL，报告里可直接查看 |
| CI 环境弹出浏览器卡死 | 提供 `--headless` 开关，与本地演示模式解耦 |

> 关键原则：**不稳定逻辑只能存在于 Page 层，不能出现在用例层**。
> 用例层只写「做什么、期望什么」，一旦用例里出现重试、等待、判断分支，
> 这条用例的可信度就已经下降了。

## 6. 缺陷 → 用例的闭环

| 缺陷 | 现象 | 沉淀的回归用例 |
|---|---|---|
| 分类点击异常 | 点击「最新」后内容区偶发空白，链接数量骤降 | `test_23_home_links_after_category_click` |
| 导航点击不跳转 | 「高级搜索」点击后停留原页 | `test_08`，并在 `NavigationPage` 内加 href 兜底 |

这是自动化测试相对手工测试最大的价值点：**一次发现，永久回归**。

---

## 7. 未覆盖范围与风险（诚实清单）

- **登录态**：站点需微信扫码，无法自动化，只能由 `--pause-login` 人工介入。
  这是当前框架最大的限制，也是它不能直接上 CI 全量跑的原因。
- **文章详情页**：仅校验入口链接格式（`test_29/030`），未进入详情页校验正文。
- **搜索结果正确性**：只校验"能提交、能到结果页"，未校验结果条目是否真的相关。
  要校验必须引入接口层或结果断言规则，属于下一阶段工作。
- **多浏览器/响应式**：仅在 Chrome + 1920×1080 下验证。

---

## 8. 后续演进方向

1. 引入 `pytest-xdist` 做用例并行，压缩回归时长；
2. 用 `pytest-rerunfailures` 对已知 flaky 用例单独标记重跑，而不是全局重试掩盖问题；
3. 接入 requests 做接口层校验，把"结果是否相关"这类断言从 UI 层下沉到接口层；
4. 用 Docker + 独立的测试账号打通 CI 全量回归。
